## 0. 검토 방법과 한계

| 항목 | 방법 |
|---|---|
| 코드 | 두 저장소 전량 정독(law 1,501줄 · legal-ultra 1,213줄) 후 결함 가설마다 재현 |
| 법령 데이터 | legalize-kr 실저장소(HEAD 2026-09-23) 부분 클론 — 3,050개 법령 디렉터리 목록 + 9개 법령 원문 |
| 판례 데이터 | precedent-kr 실저장소 파일 목록 124,980건 + 원문 6건 |
| DRF API | 이 환경에서 `www.law.go.kr`·`open.law.go.kr` 가 네트워크 정책으로 차단(프록시 403). 대신 ① 제3자 라이브 실측 문서·응답 픽스처([rubatoyd/law-openapi-mcp](https://github.com/rubatoyd/law-openapi-mcp), 2026-09-08), ② 독립 구현([chrisryugj/korean-law-mcp](https://github.com/chrisryugj/korean-law-mcp)) 소스와 교차 확인, ③ 모의 응답으로 코드 경로 재현, ④ 실제 차단 상태로 장애 동작 재현 |
| 예시 판례 | 웹 검색 + precedent-kr 사건명으로 교차 확인 |

심각도: **치명** = 가짜 인용 통과·잘못된 법을 현행으로 제시 / **높음** = 기능이 조용히 틀림·크래시 / **중간** = 성능·이식성 / **낮음** = 문서·형식.

## C. 통합 설계 (v2)

```
                         ┌──────────── legal_swarm.py (작업판: DAG · 역할 · 게이트 · 예산) ─────────────┐
 lead_counsel ─ init ──▶ │ T1 statute ─┐                                                               │
   (Agent 도구로         │ T2 precedent ┴▶ T3 risk(Devil's Advocate) ▶ T4 draft ▶ T5 audit ▶ T6 finalize│
    서브에이전트 배정)   └───────┬──────────────────────────────────────────┬──────────────────────────┘
                                 │ submit/audit 마다 재검증                   │ 부록 A~C 시스템 생성
                                 ▼                                            ▼
                     citations.py (추출 → 병렬 검증 → PASS/FAIL/INCOMPLETE/NO_CITATIONS)
                       ├─ legal_engine.py   legalize-kr: 조·항·호·목, 삭제, 시행일(as-of), 위임, 검색
                       ├─ precedent_engine.py precedent-kr: 사건번호·법원·선고일 색인(오프라인), 판시 원문
                       └─ law_api.py        DRF: 헌재·해석례·부처 해석·위원회·행정규칙·자치법규·3단비교·교차확인
```

- **출처 우선순위**: 로컬 미러(빠르고 오프라인·결정론적) → DRF(미러에 없는 자료, 약칭 해석, 교차확인).
- **fail-closed**: 확인 못 한 것은 통과가 아니다. 대신 "없음"과 "확인 불가"를 구분해 누명을 씌우지 않는다.
- **역할 통합**: law 의 반대논리 감사관(Devil's Advocate)을 legal-ultra 의 작업판에 T3 로 넣어 6개 역할.
- **판정의 소유권**: 초안 작성자·감사관은 판정 문구를 쓰지 않는다. 판정은 `audit`/`finalize`가 검증기 결과로 생성.

## E. 남은 한계 (정직하게)

1. DRF 경로는 이 환경에서 라이브로 시험하지 못했다(제3자 실측 픽스처·모의 응답으로 시험). 사용 전 `legal.py api-probe`.
2. 전체 이력이 없는 미러의 시행일 판정은 개정표시 기반 **추정**이다(보고서에 '추정'·경고로 표시). 정밀 판정은 `setup --full-history` 또는 DRF.
3. 인용 추출은 정규식 기반이다. 비표준 표기는 통과하지 않고 `UNRESOLVED`로 떨어진다(조용히 넘어가지 않음).
4. "공개 판례 DB에 없음"은 "존재하지 않음"이 아니다(미공개 판결). 검증기는 원문 확보 전 인용 금지로 안내한다.
5. 검증기는 법리 적용의 타당성을 판단하지 않는다 — 반대논리 감사관·독립 감사관·변호사의 몫.
6. Windows 실기 테스트는 하지 못했다(경로는 `pathlib`, 출력은 UTF-8 재설정으로 대비).
